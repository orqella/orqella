# Orqella module specification (API v1)

A module is a self-contained git repository that provides a dashboard page, an
overview card, or both. It must not modify the daemon.

## Package

```text
my-module/
├── module.toml
├── ui/
│   ├── index.html        # page entry (optional)
│   ├── overview.html     # overview card entry (optional)
│   └── settings.html     # custom Modules-tab UI (optional)
├── backend/              # optional sidecar files
├── README.md
└── AGENTS.md             # recommended; generated by the builder
```

`module.toml`:

```toml
schema = 1
id = "com.example.my-page"
name = "My page"
version = "0.1.0"
api_version = "1"
description = "What this page does."
entry = "ui/index.html"     # optional if overview is present
overview = "ui/overview.html" # optional card entry
settings = "ui/settings.html" # optional custom Modules-tab UI
overview_default = true      # whether the card starts visible
page_default = true          # whether the page tab starts visible
icon = "ui/icon.svg"         # optional
node_scope = "node"           # node | aggregate | hub
permissions = ["node.metrics"]

[ui]
surface = "page"              # page | app
overview_width = 2            # preferred card width in grid columns
overview_height = 3           # preferred card height in grid rows

[backend]
kind = "none"                 # none | sidecar
# command = ["python3", "backend/server.py"]
# health_path = "/health"
# ready_timeout_ms = 15000
# read_paths = ["~/.config/my-service"]  # optional read-only host paths
# sandbox = false  # opt out of the sidecar sandbox
# platforms = ["linux"]  # optional sidecar allow-list

# Optional prebuilt sidecar executables selected by host platform:
# [[backend.artifacts]]
# platform = "linux-x86_64"
# url = "https://example.com/orqella-sidecar-linux-x86_64"
# sha256 = "..."
# args = ["--serve"]          # optional

[[config.fields]]
key = "refresh_ms"
type = "number"               # boolean | number | text | select
label = "Refresh interval"
default = 3000
min = 1000
max = 60000
step = 500
help = "How often the page refreshes."
```

A module must define `entry`, `overview`, or both. Modules with only an overview card do not appear in the page navigation. `page_default = false` keeps a page out of the tab list until the user enables it in Settings → Modules; the page remains available from Settings when enabled. Page tabs and dashboard tabs are reordered together by dragging tab grips in the sidebar (or the mobile menu) while editing any dashboard. Dashboard order is shared with other clients of the daemon; the interleaved sidebar order and module page visibility remain per device.

Overview cards declare a preferred size in dashboard grid cells with `ui.overview_width` and `ui.overview_height` (defaults: `2` columns by `3` rows). A dashboard uses that size when a device has no saved override. Choose a size that fits the card's normal content without requiring an internal scrollbar; users can move and resize cards per device from **Edit** on the Overview or a custom dashboard. The set of visible cards on a custom dashboard is shared with every client; Overview visibility and every dashboard's card positions remain per device. Cards keep explicit grid positions, so moving or resizing one does not reflow the others; empty cells stay empty.

Custom dashboards are shell pages, not modules. They have no manifest, page entry, sidecar, or permissions. Users create, rename, and delete them in **Settings → Dashboards**; the protected Overview dashboard is always present and cannot be deleted. The daemon stores custom dashboard definitions and card selection, so every client connected to the same machine sees the same dashboards. Card layout stays in each client's local storage.

### Module settings

`[[config.fields]]` declares values that are rendered automatically on the Settings page. Supported field types are `boolean`, `number`, `text`, and `select` (with `options = [{ value, label }]`). Values are stored by the daemon and delivered to the module as `context.config`. The host validates types, numeric bounds, and select options before saving.

### Node scope

- `node` — the page acts on the selected machine.
- `aggregate` — the page compares multiple machines.
- `hub` — the page only makes sense on the dashboard-serving machine.

### Permissions

| Permission | Grants |
| --- | --- |
| `node.info` | Host metadata. |
| `node.metrics` | CPU, memory, load, uptime, process count. |
| `node.services` | Configured proxy mount inventory (`proxy.list`, with `services.list` as an alias). |
| `nodes.read` | Local and peer machine list. |
| `node.proxy:<mount>` | A configured proxy mount. |
| `app.open` | Ask the shell to open a dedicated app surface. |
| `agent` | Run the configured default agent, with explicit write access to a requested directory. Sensitive. |
| `media.record` | Use the shell microphone recording bridge. |
| `backend` | Call this module's sidecar. |
| `storage` | Module-private key/value storage. |
| `fs.read:<path>` / `fs.write:<path>` | Reserved: rejected until a scoped filesystem host API exists. |
| `net.fetch:<host>` | Reserved: rejected until a scoped network host API exists. |
| `secrets:<name>` | Reserved: rejected until a named-secret host API exists. |
| `node.action:<name>` | Reserved: rejected until a typed node action API exists. |

Only the permissions with a host-API implementation are accepted. Reserved
namespaces (`fs.*`, `net.fetch:*`, `secrets:*`, `node.action:*`) are rejected
with a "reserved and not implemented" error, so a module cannot collect a
grant that has no effect. `notifications`, `audit`, and `proxy.read` were
removed: they never had an implementation.

## Agent and recording APIs

### Agent hooks

Requires `agent`. The stable hook surface is:

- `agent.prompt` — start the configured default agent, optionally wait for a
  conversation id, and optionally open the conversation viewer.
- `conversation.open` — open the configured viewer for an existing agent job or
  conversation id.

Call them with `window.orqella.hooks.run(...)`; see
[`HOST_API.md`](HOST_API.md#hooks) for the parameter and result shapes. The
viewer is configured under `[agent.viewer]` and defaults to the OpenCode module
page at `/?session={session}` for the OpenCode preset. Other harnesses can use
an installed module page, a proxy-mount path template, or an external URL
template.

The lower-level `agent.start` / `agent.status` methods remain available for
background jobs that do not need a conversation viewer. `agent.start` accepts
`{ "prompt": "…", "root": "~/Projects/project" }` and runs the configured
default agent in the requested directory. It is intentionally powerful and
unsandboxed; grant it only to modules the user trusts. Poll `agent.status` with
the returned job ID. The job result includes `status`, `log`, `error`,
`workspace`, and `session_id` when the harness exposes one.

### `media.record.start` / `media.record.stop`

Requires `media.record`. These are handled by the trusted shell, not by the daemon process, because module iframes have opaque origins. `start` prompts for microphone access; `stop` returns `{ audio, mime, size }` with base64 audio. Modules should send the clip to their sidecar for transcription.

### Module dependencies

Modules may declare other modules they build on:

```toml
[[dependencies]]
id = "voice-assistant"
optional = true
reason = "Adds the Assist conversation agent and Whisper STT pipeline."

[[dependencies]]
id = "terminal"
optional = false
reason = "Opens a terminal tab from the page."
```

Dependency IDs are installed module IDs. A required dependency is declared with
`optional = false`. Orqella validates the IDs, rejects self-dependencies and
duplicates, and shows the dependency state in Settings → Modules.
Missing dependencies are labeled, but this first pass is metadata only: it does
not automatically install or block removal. Future update and install flows can
use the declarations for ordering and prompts without changing module manifests.

Declare a dependency when the module actually integrates with another module's
surfaces or backend. Do not use dependencies to share source code; modules
remain independent git repositories.

## App surfaces

A module that forwards an external web app should use a configured proxy mount
and the generic `app.open` handoff rather than implementing a proxy in the
module or adding a core route. The browser client places full apps on isolated
origins (explicit `__ORQELLA_APP_ORIGINS` entries or a wildcard
`__ORQELLA_APP_ORIGIN_SUFFIX`) and maps their root-relative HTTP, WebSocket, and
SSE traffic through the authenticated WebRTC transport.

Browser application data is direct WebRTC only. Managed relay credentials are
used strictly for bootstrap/signaling, and relayed application connections are
rejected. Native clients are the supported path when direct WebRTC is not
available. Apps requiring their own service worker are not currently supported
by the isolated app worker. Use `app.open` with optional `handoff`/`path` for
app login or deep links.

## UI runtime

- Page assets are served under `/m/<id>/`; overview assets under `/m/<id>/overview`; custom settings under `/m/<id>/settings`. Runtime files under the module's top-level `data/` directory are never served as static assets.
- The page, card, or settings UI runs in an iframe with an opaque origin.
- The daemon injects `<base>` and the Orqella SDK into HTML.
- Relative CSS/JS paths are resolved relative to the entry file's directory.
- Link `/assets/theme.css` and `/assets/module.css` before the module's own CSS. `module.css` provides the core primitives (`.card`, `.button`, `.field`, `.chip`, `.empty`, `.row`, `.muted`, `.grid-2`, `.metric`, `.icon-button`) so the page follows the selected theme. Use theme tokens for module-specific styles rather than a fixed palette.
- Use `window.orqella.ready(callback)` and `window.orqella.call(method, params)`.
- `context.surface` is `page`, `overview`, or `settings`; `context.config` contains this module's saved settings. `context.theme` is `dark`/`light` and `context.theme_id` is the selected theme id.
- The page does not receive the dashboard cookie or the module token.
- The shell delegates clipboard-write to module frames. Microphone recording goes through the host `media.record` bridge; module frames do not receive microphone permission directly.
- The bridge is request/response. A page may connect to `ws://<host>/m/<id>/ws/<path>` (or `/n/<node>/m/<id>/ws/<path>` for a remote module); the daemon forwards the authenticated WebSocket to the module sidecar at `/ws/<path>`.

## Sidecar

When `backend.kind = "sidecar"`:

- the daemon allocates a loopback port;
- sets `ORQELLA_MODULE_PORT`, `ORQELLA_MODULE_TOKEN`, `ORQELLA_MODULE_ID`, `ORQELLA_NODE`, `ORQELLA_HOST_HOME`, and `ORQELLA_MODULE_CONFIG` (the module's saved config as JSON);
- sets `HOME` to `<module>/data/home` and moves legacy home directories there once on first start;
- binds each `backend.read_paths` entry read-only inside the sandbox;
- starts the command in the module directory;
- waits for `GET health_path` with `X-Orqella-Module-Token`;
- proxies `backend.request` calls to it.

The sidecar is a real local process running as the logged-in user. The daemon policy controls sandboxing and memory limits by default. A module may set `[backend] sandbox = false` when it needs local desktop, keyring, model, or setup access; this is a trusted-code decision because the sidecar runs unsandboxed as the logged-in user. The permission review shows an explicit unsandboxed warning and requires an acknowledgment before it grants `backend`. On Linux, sandboxing uses bubblewrap with a read-only system filesystem, a writable module directory, private `/tmp`, and an address-space limit. On macOS, sandboxing uses a sandbox-exec profile. On Windows, the Job Object applies lifecycle and memory limits but not filesystem isolation. Memory limits also apply to unsandboxed Linux and Windows sidecars; macOS has no per-sidecar memory cap. Every current first-party module opts out of filesystem sandboxing.

`backend.platforms` is an optional allow-list (`linux`, `macos`, `windows`). On hosts outside the list the sidecar is not started; the module still installs and its non-backend surfaces continue to work. Modules should hide backend-only UI on those hosts.

### Python setup

Python sidecars can declare their interpreter and dependencies:

```toml
[backend]
kind = "sidecar"
command = ["python3", "backend/server.py"]
python = ">=3.11"
requirements = "backend/requirements.txt"
```

`backend.python` is a major/minor version requirement (`>=`, `>`, `<=`, `<`, or
`==`). Orqella searches `python3`, versioned Python binaries, and on Windows the
`py` launcher. A command beginning with `python` or `python3` is checked for a
usable interpreter even without these fields. If the requirement is missing,
the sidecar fails with an actionable message instead of a crash loop.

When `backend.requirements` is present, Orqella creates a managed virtual
environment at `data/.sidecar-venv` using the selected interpreter and runs
`pip install -r` on first start and whenever the requirements file changes. The
sidecar then runs from that virtual environment. This is why a module can ship a
`requirements.txt` without assuming the user's global Python packages.

The requirements install needs network access the first time. If Python is
missing or too old the module shows the interpreter error and remains
retryable; install a compatible Python and restart the module. For a fully
interpreter-free distribution, use prebuilt sidecar artifacts instead.

### Prebuilt sidecar artifacts

A sidecar can use a prebuilt executable instead of an interpreter command. Each
artifact declares an exact `platform` in `<os>-<arch>` form, exactly one of a
direct HTTP(S) `url` or a module-relative `path`, and the SHA-256 digest of the
binary:

```toml
[backend]
kind = "sidecar"
health_path = "/health"
ready_timeout_ms = 15000

[[backend.artifacts]]
platform = "linux-x86_64"
url = "https://example.com/releases/orqella-sidecar-linux-x86_64"
sha256 = "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef"
args = []

[[backend.artifacts]]
platform = "macos-aarch64"
path = "backend/bin/sidecar-macos-aarch64"
sha256 = "fedcba9876543210fedcba9876543210fedcba9876543210fedcba9876543210"
```

`path` artifacts stay in the module repository and are checksum-verified and
made executable in place. They let a private module ship its own binaries without
a public download host. The module installer must include the referenced files.

The host platform comes from the daemon target OS and architecture. Supported
OS names are `linux`, `macos`, and `windows`; common architecture names are
`x86_64`, `aarch64`, `arm`, and `x86`. On macOS under Rosetta, the daemon uses
the architecture it is running as.

When a matching artifact exists, the daemon:

1. for `url` artifacts, downloads it to the module's
   `data/.sidecar-artifacts/` directory and reuses the cached file later;
2. for `path` artifacts, uses the module-relative file directly;
3. verifies the SHA-256 digest and marks it executable;
4. runs the artifact with its `args` and the environment described below.

If no artifact matches the host, `backend.command` is used as a fallback. A
sidecar must define at least one of `backend.command` or `backend.artifacts`.
Artifact URLs are fetched without extra authentication headers. Private GitHub
release assets are therefore not supported directly; use a public/internal
artifact host or a pre-signed URL. Downloads are capped at 256 MB. The cache is
runtime data; it is excluded from module packages and support bundles, while a
module-data backup may include it. Deleting it is safe; it is downloaded again
on the next sidecar start.

## Installation and packages

Every installed module is its own git checkout. The module source is never part
of the Orqella repository.

- Install from a local folder or a git URL with an optional branch.
- Git URL installs clone the repository and keep `origin`; local folder installs
  are initialized as repositories when needed.
- Modules can also be exported as a `.orqella-module.zip` package and imported
  on another machine.
- The validator checks the manifest, entry, permissions, backend shape, and ID.
- Existing grants are preserved on update. New permissions appear as pending
  and must be reviewed in the Permissions sheet before the module can use them.
- A failed update restores the previous module directory from `data/backups/modules`.
- An existing module `data/` directory is preserved across updates.
- A module update that removes a permission drops the corresponding grant.
- `data/`, `.venv/`, `node_modules/`, `target/`, `__pycache__/`, and
  `sidecar.log` are ignored by the module repository.

See [`MODULE_REPOS.md`](MODULE_REPOS.md) for update, checkpoint, publish, and the
GitHub App flow.

## Git development

Modules are repositories by default. `orqella module new` initializes and
commits the scaffold; AI edits are committed in the staging workspace before
validation and install. Keep user data out of commits. Use
`orqella module checkpoint` for a local commit and `orqella module publish` to
create or update the GitHub repository.

## Compatibility

- `schema` must be `1`.
- `api_version` must be `1` for this daemon.
- Unknown fields should be preserved by tooling where possible.
- A module should declare platform restrictions in its README if it cannot work on all supported platforms.
